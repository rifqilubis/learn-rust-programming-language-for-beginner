Lesson 02 Basics 15 min

Variables, mutability, and shadowing

Rust makes you say when a value can change. That one word removes a whole category of bugs, and it takes ten minutes to get used to.

On this page

  1. A binding is immutable by default
  2. When it must change, say so
  3. Shadowing is a different tool
  4. Constants
  5. Naming
  6. Exercise

01A binding is immutable by default

let creates a binding. Unless you say otherwise, the name cannot be reassigned, and the compiler refuses the second assignment.

Try adding apples = 4; on the next line and running it. The compiler stops you with cannot assign twice to immutable variable and points at both the declaration and the reassignment, so you can see the two places that disagree.

This is not a limitation to work around. Most values in a program never change after they are created, and the compiler is enforcing that fact for free.

02When it must change, say so

mut marks a binding as changeable. It is a promise that this value has a reason to move.

Use mut where the value genuinely changes, not everywhere to silence the compiler. A file where every binding is mut tells you nothing about which state is actually in motion.

03Shadowing is a different tool

You can declare the same name again with a new let. The old binding is not changed, it is hidden, and the new one can even have a different type.

Shadowing is how you keep a name while changing what it means, for example parsing text into a number and keeping the same name:

The difference from mut is type and intent. mut means the same value changes. Shadowing means a new value takes over the name, and the old one is gone.

04Constants

const declares a value fixed at compile time. It needs a type, it lives for the whole program, and by convention its name is upper case.

Use const for values that are the same in every run. Use let for everything computed at runtime.

05Naming

Rust style is not a matter of taste here, the compiler will warn you. Bindings and functions use snake_case, types and enums use UpperCamelCase, and constants use SCREAMING_SNAKE_CASE.

Names are read far more often than they are written, so prefer remaining_attempts over n once the meaning is not obvious from the line above.
