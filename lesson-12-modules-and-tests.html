Lesson 12 Real programs 16 min

Modules, tests, and what next

Split code into modules, prove it works with tests, and then go build something. The last lesson is mostly about the habit.

01Modules are namespaces

mod groups related items and controls what is visible outside. Everything is private by default, and pub opens one item at a time.

The function is reachable as text::slugify because it is pub. Drop the pub and main can no longer see it.

02Splitting into files

When the module grows, move it to src/text.rs and keep the declaration in main.rs. The file becomes the module body.

src/
├── main.rs      mod text;
└── text.rs      pub fn slugify(...)

A folder works the same way when the module has submodules: src/text/mod.rs, or src/text.rs with a src/text/ folder beside it. Pick one and stay consistent.

03Tests live next to the code

A #[cfg(test)] module is compiled only for tests, so it costs nothing in the shipped program. use super::* pulls in everything from the parent module.

Run them with cargo test. Each test is a function that fails if an assertion fails, and the runner reports how many passed.

04assert, assert_eq, assert_ne

Three macros cover almost every check. The equality ones print both values when they fail, which is why they beat a bare assert!(a == b).

05What to build next

Reading more lessons has diminishing returns now. Pick one of these and finish it, badly, then improve it. That loop teaches more than any tutorial.

  • A command line tool that reads a file and counts words, using std::fs and std::env.
  • A to-do list stored as JSON, which means your first dependency and your first serde derive.
  • A small HTTP server with axum or actix-web, returning one page and one JSON endpoint.
  • The rustlings exercises, which are small fixes to broken programs and map well onto what you just learned.

Two habits carry you through the first month. Read the compiler error before changing code, and write the test that reproduces a bug before fixing it.

06Where the language reference lives

Four places worth bookmarking, all free and all current:

  • The Rust Programming Language, the official book this course follows in spirit.
  • The standard library documentation, where every method has a runnable example.
  • Rust by Example, for when you want to see a construct rather than read about it.
  • The Rust Playground, which is the same service this site uses to run your code.
The compiler is the teacher

Rust's error messages are written by people who expect you to read them. When one does not make sense, rustc --explain plus the error code gives you a full page on that exact mistake.

07Exercise

Implement fn word_count(text: &str) -> usize so it counts whitespace-separated words, and write three tests of your own: a normal sentence, empty input, and input with extra spaces. The checker runs your tests, then hidden ones against sentences you have not seen. It also runs your tests against a broken word_count: all three have to fail there, or they are not checking anything.

The checker calls these

fn word_count(text: &str) -> usize
three #[test] functions of your own

What runs

Your three tests, then hidden ones that call word_count with sentences you have not seen. All of them have to pass. Your tests are also run against a deliberately broken word_count: if they still pass there, they are not testing anything.

Stuck?

Work through these in order

  1. First make word_count work: text.split_whitespace() gives an iterator of words, and .count() turns it into a number.
  2. Replace each todo!(...) with one real assertion. assert_eq!(word_count("one two three"), 3); is the shape; do the same for "" and for a string with extra spaces.
  3. Your tests need to fail on a wrong implementation, so assert a specific count rather than just that the function runs. The checker runs them against a deliberately broken word_count to prove that.

Short version: text.split_whitespace().count() does the counting in one line. An assertion is assert_eq!(word_count("one two three"), 3);. Run the checker with the todo!() calls still in place once, so you see what a failing test looks like.

Reference solution

Reading or loading this does not unlock the lesson. The checker still has to run and pass your code, and loading it replaces what is in the editor.

fn word_count(text: &str) -> usize {
    text.split_whitespace().count()
}

fn main() {
    println!("{}", word_count("one two three"));
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn counts_words() {
        assert_eq!(word_count("one two three"), 3);
    }

    #[test]
    fn counts_nothing_in_empty_text() {
        assert_eq!(word_count(""), 0);
    }

    #[test]
    fn ignores_extra_spaces() {
        assert_eq!(word_count("  two   words "), 2);
    }
}
